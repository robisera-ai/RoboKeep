### 1. Cartella dati stabile

**Problema:** oggi `config.json` e `lastresults.json` stanno accanto all'eseguibile
([ConfigStore.DefaultConfigPath](../../../src/RoboKeep.Core/Services/ConfigStore.cs)).
Si perdono pulendo `bin/obj`; in `C:\Program Files` la cartella è in sola lettura.

**Soluzione:** risoluzione della *data root* all'avvio.

- Se accanto all'exe esiste un file **`portable.flag`** → data root = cartella dell'exe
  (modalità portatile, comportamento attuale).
- Altrimenti → data root = **`%APPDATA%\RoboKeep`** (`Environment.SpecialFolder.ApplicationData`),
  creata se assente.

`config.json` e `lastresults.json` risiedono nella data root. `LogRoot`/`TempRoot`, se vuoti
in `AppSettings`, hanno default sotto la data root (`<dataRoot>\logs`, `<dataRoot>\temp`); se
l'utente li ha già impostati, restano invariati.

**Migrazione (best-effort):** al primo avvio in modalità `%APPDATA%`, se lì non esiste
`config.json` ma ne esiste uno accanto all'exe, viene copiato (insieme a `lastresults.json`
se presente). Nessuna cancellazione dell'originale.

**Nuovo servizio Core `AppDataLocator`:**

```
public sealed class AppDataLocator
{
    // Parte PURA e testabile: nessun IO.
    // portableFlagPresent: esiste portable.flag accanto all'exe?
    public static string ResolveDataRoot(string exeDir, string appDataDir, bool portableFlagPresent)
        => portableFlagPresent ? exeDir : Path.Combine(appDataDir, "RoboKeep");

    // Wrapper IO (usato dall'app): legge l'esistenza del flag, crea la cartella,
    // esegue la migrazione best-effort. Sottile, non unit-testato.
}
```

- `AppHost` usa `AppDataLocator` per costruire `ConfigStore` e `LastResultStore` con i
  percorsi nella data root, al posto di `DefaultConfigPath`.
- **CLI/scheduler:** `RoboKeep.exe --run-all` risolve la stessa data root **se eseguito
  come lo stesso utente** (stesso `%APPDATA%`). Caso documentato; chi pianifica sotto altro
  account usa `portable.flag`.
- **README (IT + EN):** la frase "portatile di default" diventa "dati per-utente in
  `%APPDATA%\RoboKeep`; modalità portatile con un file `portable.flag` accanto all'exe".

**Test (TDD):** `ResolveDataRoot` — flag presente → exeDir; flag assente → `%APPDATA%\RoboKeep`.

### 2. Pre-check pre-avvio (avvisa, non blocca)

**Nuovo servizio Core `PreflightChecker`**, separato in raccolta dati (IO) e valutazione (pura).

Modello del risultato:

```
public enum PreflightSeverity { Info, Warning }

public sealed record PreflightWarning(PreflightSeverity Severity, string MessageKey, string Detail);

// Dati raccolti (IO) e passati al valutatore puro:
public sealed record PreflightInputs(
    bool DestinationReachable,
    long FreeBytes,
    long MinFreeBytes,
    long? SourceSizeBytes); // null se la scansione non è stata fatta o è troppo lenta
```

**Valutazione pura `PreflightChecker.Evaluate(PreflightInputs) -> IReadOnlyList<PreflightWarning>`:**

- `!DestinationReachable` → **Warning** "destinazione non raggiungibile".
- `FreeBytes < MinFreeBytes` → **Warning** "spazio libero sotto la soglia minima".
- `SourceSizeBytes` valorizzato **e** `SourceSizeBytes > FreeBytes` → **Warning** "lo spazio
  libero potrebbe non bastare per la sorgente".

**Raccolta dati (IO, sottile):**

- *Raggiungibilità:* per percorso locale, esiste la radice (drive)? Per UNC, `Directory.Exists`
  sulla radice della share (la connessione credenziali è già gestita altrove).
- *Byte liberi:* `DriveInfo` / `GetDiskFreeSpaceEx` sulla destinazione.
- *Dimensione sorgente:* scansione **a tempo limitato** (`Stopwatch`, budget breve, es. 2s);
  se completa entro il budget → `SourceSizeBytes`, altrimenti `null` (si usa solo la soglia).

**UI (WPF):** al click su **Avvia / Avvia tutti**, esegue il preflight per i job coinvolti;
se ci sono Warning → dialog **"Avvia comunque / Annulla"** con l'elenco. In **`--run-all`**
(non interattivo) gli avvisi vengono **scritti nel log, senza bloccare**.

**Impostazioni:** `PreflightEnabled` (default true), `MinFreeSpaceMb` (default 1024).

**Test (TDD):** `Evaluate` — destinazione ok + spazio ok → nessun avviso; irraggiungibile →
warning; libero < soglia → warning; sorgente > libero → warning; `SourceSizeBytes` null →
nessun warning di dimensione.

### 3. Allerta backup fermo/fallito (soglia globale + GUI)

**Nuovo servizio Core `StaleBackupEvaluator`** (puro). Riusa `JobLastResult`
(`Success`, `FinishedAt`) già persistito in `lastresults.json`.

```
public enum BackupHealth { Ok, Failed, Stale, NeverRun }

public sealed record JobHealth(string JobName, BackupHealth Health);

public static class StaleBackupEvaluator
{
    public static IReadOnlyList<JobHealth> Evaluate(
        IEnumerable<string> jobNames,
        IReadOnlyDictionary<string, JobLastResult> lastResults,
        int staleAfterDays,   // 0 = disabilitato → tutto Ok tranne i Failed
        DateTime now);
}
```

Regole per ciascun job:

- nessun esito in `lastResults` → **NeverRun**;
- ultimo esito `Success == false` → **Failed**;
- `staleAfterDays > 0` e `now - FinishedAt > staleAfterDays` giorni → **Stale**;
- altrimenti → **Ok**.

**UI (WPF):** all'avvio e dopo ogni run, valutazione su tutti i job.

- Un **banner InfoBar** in cima elenca i job **Failed** e **Stale** (allarmanti); righe
  evidenziate.
- **NeverRun** mostrato come **nota neutra** (non nel banner d'allarme), per non infastidire
  sui job appena creati.

**Impostazioni:** `StaleAfterDays` (default 7; 0 = disabilita la parte "Stale").

**Test (TDD):** nessun esito → NeverRun; ultimo errore → Failed; successo vecchio oltre N
giorni → Stale; successo recente → Ok; `staleAfterDays = 0` → nessuno Stale.

### 4. Notifiche toast + icona tray

- **Toast** a fine job (in particolare su errore), se `NotificationsEnabled` (default true).
- **Tray:** icona in area di notifica con menu **Apri / Avvia tutti / Esci**; opzioni
  `MinimizeToTray` (riduci a icona invece di chiudere) e `StartMinimized` (avvio in tray).
- **Libreria:** `H.NotifyIcon.Wpf` (NuGet singolo, tray + notifiche, nativo WPF).
- Attivo **solo nell'app interattiva**, non nel run `--run-all` headless.

**Impostazioni:** `NotificationsEnabled` (default true), `MinimizeToTray` (default false),
`StartMinimized` (default false).

**Test:** logica di reduci-a-icona / scelta del messaggio toast dove isolabile; il resto è
integrazione UI (verifica manuale).

## Flusso e gestione errori

- **Avvio app:** risolvi data root → (migra se serve) → carica config/esiti → valuta salute →
  mostra banner. Errori di migrazione/lettura: best-effort, l'app parte comunque coi default.
- **Avvio job (GUI):** preflight → se warning, dialog → procedi/annulla. `--run-all`: preflight
  loggato, mai bloccante.
- **Fine job:** aggiorna `lastresults` (già esistente) → toast (se abilitato) → rivaluta salute.
- I servizi Core non lanciano per condizioni "di dominio" (destinazione assente, esito mancante):
  le rappresentano nei modelli di ritorno.
