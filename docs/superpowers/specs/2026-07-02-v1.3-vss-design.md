# Spec — v1.3 File aperti (VSS)

**Stato:** approvato (design) · **Data:** 2026-07-02
**Roadmap:** terza tappa di [2026-06-24-roadmap-design.md](2026-06-24-roadmap-design.md)

## Problema

Robocopy salta i file aperti/bloccati (PST di Outlook, database, file in uso da altri
programmi): il backup riesce ma è **incompleto**, e proprio i file più usati — quindi più
importanti — sono quelli che mancano. Volume Shadow Copy (VSS) congela il volume in uno
snapshot di sola lettura: copiando dallo snapshot, anche i file aperti si leggono integri.

## Decisioni prese (brainstorming)

1. **Elevazione**: UAC solo quando serve. RoboKeep resta un processo utente; solo il run di
   un job con VSS attivo mostra il prompt UAC (una volta per run). Le esecuzioni pianificate
   con privilegi elevati non mostrano nulla.
2. **Attivazione**: opzione per job (casella nell'editor), non automatica. Il wizard la
   propone con una domanda dedicata.
3. **Fallback**: se lo snapshot non si può creare (UAC negato, servizio non disponibile,
   volume non idoneo), il job **prosegue con la copia normale** e il log/riepilogo segnala
   chiaramente che i file aperti verranno saltati. Un backup parziale batte nessun backup
   (stesso principio del fallback versioning senza hard-link).
4. **Tecnica**: WMI `Win32_ShadowCopy` (pacchetto `System.Management`, puro .NET, zero DLL
   native) con **helper elevato = lo stesso RoboKeep.exe** rilanciato con un flag CLI.
   Il helper resta vivo per tutta la durata del job → **1 solo UAC per run**.
   Scartate: AlphaVSS (DLL native, potenza non necessaria), `vssadmin` (solo Windows Server).

## Architettura

### Flusso di un run con VSS

```
RoboKeep (utente)                          RoboKeep --vss-helper (elevato, UAC)
─────────────────                          ────────────────────────────────────
1. BackupRunner: job.UseVss && !dryRun
2. VssSession.Open: scrive request.json
   {volume, parentPid} e lancia il helper ─→ 3. legge request.json, crea snapshot WMI
                                            4. symlink <sess>\source → \\?\GLOBALROOT\...\
                                            5. scrive ready.json {shadowId, linkPath}
6. legge ready.json (timeout 60s)           (resta in attesa di release.flag,
7. robocopy con sourceOverride =             sorvegliando il PID del padre)
   <linkPath>\<sottopercorso job>
8. fine job → scrive release.flag        ─→ 9. cancella snapshot + symlink, esce
```

- Il **sottopercorso** si ricava dal percorso del job relativo alla radice del volume:
  `C:\Users\robi\Documenti` su snapshot di `C:\` → `<linkPath>\Users\robi\Documenti`.
- Il symlink lo crea il helper (richiede admin), dentro la cartella di sessione
  (`<dataRoot>\vss\<guid>\`), non in posizioni globali.
- **Composizione col versioning**: VSS rimappa solo la sorgente; gli snapshot hard-link
  toccano solo la destinazione. Indipendenti, si combinano senza logica extra.
- **Anteprima (dry-run)**: mai VSS, come per il versioning.

### Componenti

| Componente | Responsabilità |
|---|---|
| `Core/Services/VssPathMapper.cs` (**puro**) | Da percorso job + radice snapshot → percorso rimappato; estrazione volume (`C:\`) dal percorso sorgente; idoneità (lettera di unità fissa sì, UNC no). |
| `Core/Services/VssSessionProtocol.cs` (**puro**) | Il protocollo file della sessione: nomi/percorsi di `request.json`, `ready.json`, `release.flag`; serializzazione/parse di `request.json` (volume, parentPid) e `ready.json` (shadowId, linkPath, errore). |
| `Core/Services/VssSession.cs` | Lato client: lancia il helper elevato (`Verb=runas`), attende `ready.json` (timeout 60s), espone `SnapshotSourcePath`; `DisposeAsync` scrive `release.flag` e attende l'uscita del helper (timeout, poi prosegue). UAC negato (Win32Error 1223) → `VssUnavailableException` con motivo. |
| `Core/Services/VssHelper.cs` | Lato elevato: crea snapshot via WMI `Win32_ShadowCopy.Create(volume, "ClientAccessible")`, interroga `DeviceObject`, crea il symlink, scrive `ready.json`; attende `release.flag` **o** morte del processo padre **o** timeout 12h; pulizia (delete WMI dello shadowId + symlink) sempre, anche su errore. |
| `Core/Services/VssLedger.cs` | Registro degli shadowId creati (file JSON nella cartella dati). Scrittura prima della creazione, rimozione dopo la cancellazione. All'apertura di ogni nuova sessione VSS, cancella gli snapshot residui di run precedenti (pattern pulizia `.inprogress`). |
| `RobocopyArgsBuilder` | Nuovo parametro `sourceOverride` (gemello del `destinationOverride` esistente) in `Build` e `BuildForceCopyPass`. |
| `BackupRunner.RunJobAsync` | Se `job.UseVss && !dryRun`: apre la `VssSession`, passa `sourceOverride`, righe `[vss]` nel log; su `VssUnavailableException` → fallback normale + avviso. |
| `App`/CLI | Nuovo flag `--vss-helper <cartellaSessione>`: esegue `VssHelper` senza finestra e termina. |
| `BackupJob` | Nuova proprietà `UseVss` (bool, default false). `Clone`/`CopyInto` aggiornati. |

### Robustezza

- **Helper orfano**: il helper riceve il PID del padre in `request.json`; se il padre muore,
  pulisce ed esce. Timeout di sicurezza 12h come ultima rete.
- **Snapshot orfani**: `VssLedger` + pulizia a inizio sessione. Se il helper viene killato
  dopo la creazione, il residuo si elimina al run VSS successivo.
- **UAC negato / WMI errore / timeout**: sempre `VssUnavailableException` → fallback copia
  normale, riga `[vss] ATTENZIONE: …` nel log, il riepilogo resta quello reale (i file
  bloccati compaiono tra i falliti/saltati come oggi).
- **Cancellazione run**: il `finally` del run chiude la sessione (release) anche su annullo.

### Idoneità e avvisi

- VSS richiede sorgente su **volume locale con lettera** (no UNC). Non idonea →
  avviso al salvataggio nell'editor e warning nel pre-check; al run, fallback + avviso.
- Windows 11 **Home**: `Win32_ShadowCopy.Create` da verificare nello smoke; se mancasse,
  il fallback garantisce comunque il comportamento corretto (avviso chiaro, copia normale).

## UI

- **Editor job**: casella "Copia anche i file aperti (VSS)" con nota "richiede conferma
  amministratore all'avvio del backup". Sotto le opzioni esistenti di copia.
- **Wizard** (passo "Casi speciali"): "Alcuni file restano aperti durante il backup
  (es. Outlook, database)?" sì/no → `UseVss`, con `InfoHint` che spiega UAC e snapshot.
- **Pre-check**: warning se `UseVss` e sorgente non idonea ("i file aperti verranno saltati:
  la sorgente non supporta gli snapshot VSS").
- **Log**: righe `[vss] snapshot creato (C:)`, `[vss] snapshot rilasciato`,
  `[vss] ATTENZIONE: snapshot non disponibile (<motivo>): i file aperti verranno saltati`.
- **Localizzazione**: tutte le stringhe nuove in 5 lingue (`Loc.cs` per la UI,
  `CoreLoc.cs` per le righe di log/riepilogo).

## Test

Unit (xUnit, senza admin né WMI):
- `VssPathMapper`: estrazione volume; rimappatura sottopercorso; idoneità (C:\ sì, UNC no,
  percorso relativo no).
- `VssSessionProtocol`: round-trip `request.json` e `ready.json` (successo ed errore);
  percorsi file sessione.
- `VssLedger`: registra/rimuove; elenca residui; file mancante → vuoto.
- `RobocopyArgsBuilder`: `sourceOverride` sostituisce la sorgente in `Build` e
  `BuildForceCopyPass`; assente → invariato.
- `BackupJob`: default `UseVss=false`; round-trip JSON config.

Smoke manuale (unica parte con admin reale):
1. Job con VSS su cartella con un file tenuto aperto/bloccato → UAC → il file viene copiato.
2. UAC negato → il job completa in copia normale con l'avviso `[vss]` nel log.
3. Kill di RoboKeep durante un run VSS → al run successivo lo snapshot residuo viene pulito.
4. VSS + versioning insieme → snapshot datato corretto, file aperto presente.

## Fuori scope (YAGNI)

- Coordinamento writer applicativi specifici (SQL/Exchange): lo snapshot ClientAccessible
  basta per PST/file bloccati.
- VSS su destinazione (non ha senso: si scrive, non si legge).
- Retry automatico con VSS quando robocopy incontra file bloccati (scartato nel brainstorming).
- Impostazioni globali VSS: nessuna, è tutto per job.
