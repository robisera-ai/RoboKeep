# v1.9 — Soglia sulle cancellazioni in mirror, copia della configurazione, firma — design

Data: 2026-09-26. Stato: approvato.

## Scopo

Chiudere i due modi più probabili di perdere dati con RoboKeep e togliere l'«editore
sconosciuto» di SmartScreen:

1. un mirror che cancella la destinazione perché la sorgente è stata svuotata per errore
   (cartella spostata, unità di rete non montata che appare vuota, formattazione sbagliata,
   ransomware);
2. un disco di backup che ha i file ma non i job: alla morte del PC la configurazione
   (job, esclusioni, credenziali, email) non è da nessuna parte;
3. l'eseguibile non firmato.

## B. Soglia sulle cancellazioni in mirror

### Cosa fa

- Vale solo per i job in **mirror** (`Mirror == true`); l'accumulo non cancella mai.
- Prima del run vero, un'anteprima `/L` **senza `/MT`** (come già fa `SnapshotService` per i
  job con versioni: con `/MT` i conteggi mentono) conta i file **extra** = presenti in
  destinazione e assenti in sorgente = quelli che il mirror cancellerebbe. Per i job con
  versioni si **riusa** l'anteprima che `SnapshotService.RunVersionedAsync` fa già contro
  l'ultimo snapshot: nessuna seconda enumerazione. Per i job senza versioni se ne aggiunge una
  contro la destinazione.
- Stima: `extra = FilesExtra`, `totale = FilesExtra + FilesSkipped + FilesCopied` (i file che
  la destinazione avrà o ha), `percento = extra * 100 / totale` (0 se totale è 0).
- Regola pura `MirrorDeleteGuard.Evaluate(extra, totale, limitePercento)` → blocca se
  `limitePercento > 0 && extra >= MinFiles (20) && percento >= limitePercento`.
- Se blocca: il run **non parte**. Chi chiama decide:
  - **Finestra**: `BackupRunner.RunJobAsync` riceve un callback opzionale
    `Func<MirrorDeleteEstimate, Task<bool>>? confirmDeletions`. Il `MainViewModel` lo
    implementa con un MessageBox sul thread UI: «Il mirror di «Documenti» cancellerebbe
    1 812 file su 2 014 (90 %) in E:\Backup\Documenti. È voluto? Sì = procedi, No = fermati.»
    Sì → il run prosegue normalmente (una sola conferma, per questo run). No → job fermato.
  - **Riga di comando / attività pianificata**: callback null → job fermato.
- Job fermato: `JobResult { Success = false, NotStarted = true, DeletionsBlocked = true,
  DeletionsBlockedDetail = "…", ExitCode = 8 (bit «file falliti»: chi guarda solo il codice vede
  un fallimento), Status = CoreLoc "Guard_Status" }`; voce di cronologia; `JobLastResult` con
  `DeletionsBlocked` + dettaglio; email come per un errore (oggetto «BLOCCATO: …»), solo se
  configurata; nel log la riga con i numeri e il perché.
- Salute del job: `BackupHealth.Failed` con tooltip dedicato («Mirror fermato: avrebbe
  cancellato N file su M (x %). Apri il job e avvialo dalla finestra per confermare»).
  L'utente sblocca **avviando il job dalla finestra** (arriva la domanda) o alzando/azzerando
  la soglia nell'editor. Nessuna nuova finestra.
- Impostazione per job: `BackupJob.MirrorDeleteLimitPercent` (int, default **20**, 0 = mai).
  Editor: campo «Ferma il mirror se cancellerebbe più del … % dei file (0 = mai)» nel gruppo
  del mirror, con spiegazione. Wizard: non chiede nulla, usa il default. Anteprima del comando
  invariata (la soglia non è un parametro di robocopy).
- Anteprima (`--dry-run` / pulsante Anteprima): nessun blocco, ma il riepilogo dice «Il mirror
  cancellerebbe N file (x %): sopra la soglia del job» quando è il caso.
- Costo: un'enumerazione in più per i mirror senza versioni. Su cartelle enormi può essere
  decine di secondi: la riga «[controllo] anteprima delle cancellazioni…» lo dice nel log.

### Casi limite

- Destinazione vuota (primo run): extra 0 → passa.
- Sorgente assente: robocopy fallisce da solo senza cancellare (già così), la guardia non entra.
- Errore hardware in anteprima: già gestito (si ferma prima).
- Forza-copia: la seconda passata non cancella nulla; la stima usa solo la prima.
- `MinFiles`: 20 file. Sotto, la guardia non scatta anche con il 100 %.

## A. Copia della configurazione nella destinazione

### Cosa fa

- Dopo ogni run **riuscito e non in anteprima** di un job con destinazione su **disco locale**
  (lettera di unità; le share UNC sono escluse), RoboKeep scrive nella **radice del volume di
  destinazione** la cartella `RoboKeep-config\` con:
  - `config.json`: la configurazione completa nel formato di `ConfigTransfer.Export`;
  - `LEGGIMI.txt` (multilingua: it + en nello stesso file): che cos'è, da quale PC
    (`Environment.MachineName`) e quando, come si ripristina (RoboKeep → Impostazioni →
    Importa configurazione), nota che le password vanno reinserite su un altro PC.
- Una copia per disco, sovrascritta a ogni run: vince l'ultimo job. Best-effort: qualunque
  errore (disco in sola lettura, spazio, permessi) produce una riga nel log, mai un fallimento.
- Nessun mirror può cancellarla: sta fuori dalle cartelle dei job. Se un job ha come
  destinazione **la radice stessa** del disco (`E:\`), `RobocopyArgsBuilder` aggiunge sempre
  `/XD RoboKeep-config` (costante `ConfigMirror.FolderName`), così il mirror la ignora.
- Impostazione globale `AppSettings.ConfigCopyToDestination` (bool, default **true**), casella
  in Impostazioni: «Salva una copia della configurazione sui dischi di backup».
- Privacy: la copia contiene percorsi, indirizzi email e password cifrate DPAPI (illeggibili su
  un altro PC o account). Guida cap. 17 lo dice.

## C. Firma del codice (SignPath Foundation)

- Richiesta a SignPath Foundation (progetto open source, licenza MIT, repo pubblico) fatta dal
  maintainer: testo pronto in `docs/signpath/richiesta.md` (in inglese, con i dati da
  compilare). La valutazione richiede settimane: si avvia subito, in parallelo ad A e B.
- Workflow `release.yml`: dopo il publish e prima dello zip, se la variabile di repository
  `SIGNPATH_ENABLED == 'true'`, invia `RoboKeep.exe` (framework-dependent e self-contained) a
  SignPath con `signpath/github-action-submit-signing-request`, attende il file firmato e lo
  sostituisce nella cartella prima di `Compress-Archive`. Segreti: `SIGNPATH_API_TOKEN`;
  variabili: `SIGNPATH_ORGANIZATION_ID`, `SIGNPATH_PROJECT_SLUG`, `SIGNPATH_POLICY_SLUG`.
  Con la variabile assente il workflow è identico a oggi.
- README (5 lingue) e guida cap. 16: la frase su SmartScreen cambia **solo** quando la prima
  release firmata è uscita; fino ad allora resta com'è.
- Onestà: la firma mostra «SignPath Foundation» al posto di «editore sconosciuto»; la
  reputazione SmartScreen si accumula comunque con i download. Non promettere che l'avviso
  sparisce subito.

## Come è fatto

- `RoboKeep.Core/Services/MirrorDeleteGuard.cs`: `record MirrorDeleteEstimate(string JobName,
  string Destination, long Extra, long Total, int Percent, int LimitPercent)`;
  `const int MinFiles = 20`; `static MirrorDeleteEstimate Estimate(job, RobocopyCounts)`;
  `static bool ShouldBlock(MirrorDeleteEstimate)`. Puro, testato.
- `BackupRunner.RunJobAsync(..., Func<MirrorDeleteEstimate, Task<bool>>? confirmDeletions =
  null)`: per i mirror senza versioni esegue l'anteprima e applica la guardia; per i mirror con
  versioni `SnapshotService.RunVersionedAsync` riceve lo stesso callback e applica la guardia
  ai conteggi dell'anteprima che già fa (prima di decidere «niente da fare»).
- `JobResult.DeletionsBlocked/DeletionsBlockedDetail`, `JobLastResult.DeletionsBlocked/
  DeletionsBlockedDetail`, `RunHistoryEntry` con esito «bloccato» (riusa il log).
- `EmailService.BuildSubject/BuildBody`: caso bloccato.
- `RoboKeep.Core/Services/ConfigMirror.cs`: `const string FolderName = "RoboKeep-config"`;
  `static string? TargetFolder(string destination)` (null per UNC o radice non trovata);
  `static void Write(AppConfig config, string destination, IProgress<string>? progress)`;
  `static string ReadmeText(string machine, DateTime when)`. Chiamata da `BackupRunner` a fine
  run riuscito quando `Settings.ConfigCopyToDestination`.
- `RobocopyArgsBuilder`: `/XD RoboKeep-config` sempre presente quando la destinazione è una
  radice di volume.
- `MainViewModel`: callback di conferma (MessageBox sul thread UI, `Owner` finestra principale);
  tooltip di salute per `DeletionsBlocked`.
- `JobEditorWindow` + `JobEditorViewModel`: campo soglia. `SettingsWindow`: casella copia config.
- `CoreLoc` (5 lingue): stato, riga di log, oggetto email; `Loc` (5 lingue): domanda, tooltip,
  etichette editor/impostazioni.
- Guida: cap. 05 (mirror) o dove si spiega il mirror → la soglia; cap. 14 impostazioni →
  copia config; cap. 16 → «Il job dice mirror fermato»; cap. 17 → privacy della copia.
  CHANGELOG Unreleased.

## Test

- `MirrorDeleteGuardTests`: sotto soglia, sopra soglia, sotto MinFiles con 100 %, limite 0,
  totale 0, percentuale arrotondata.
- `BackupRunner`: mirror senza versioni che supererebbe la soglia con callback null → risultato
  bloccato, robocopy vero mai invocato (finto runner che registra le chiamate); con callback
  che risponde true → run eseguito; accumulo → nessuna anteprima aggiuntiva.
- `SnapshotService`: anteprima esistente che supera la soglia → bloccato prima del clone.
- `ConfigMirrorTests`: `TargetFolder` (lettera, UNC → null, radice), `Write` su cartella
  temporanea (crea config.json e LEGGIMI.txt, sovrascrive), errore di scrittura → nessuna
  eccezione.
- `RobocopyArgsBuilderTests`: `/XD RoboKeep-config` presente solo con destinazione radice.
- Email: oggetto/corpo del caso bloccato.
- UI: prova manuale (svuotare una sorgente di prova, avviare il mirror, vedere la domanda;
  da riga di comando vedere il blocco e l'icona; verificare `E:\RoboKeep-config`).

## Fuori scopo

Ripristino guidato, sentinella dei backup non eseguiti, versioni senza hard-link, delta a
blocchi. Restano nella lista dei lavori aperti.
