# RoboKeep v1.2 — Versioning (snapshot hard-link)

**Stato:** approvato (brainstorming) · **Branch:** `v1.2-versioning` · **Data:** 2026-06-28
**Roadmap:** seconda tappa di [2026-06-24-roadmap-design.md](2026-06-24-roadmap-design.md)

> Obiettivo: conservare uno **storico datato** dei backup. Ogni esecuzione produce uno
> snapshot navigabile; i file immutati sono **hard-link** condivisi tra le date (spazio
> occupato una sola volta). Solo NTFS locale, ritenzione semplice, ripristino aprendo la
> cartella in Esplora risorse.

---

## Meccanismo (clona → rompi-cambiati → robocopy)

> **Nota dallo spike (gate):** robocopy, aggiornando un file in destinazione, lo **modifica
> sul posto** (stesso inode), NON lo sostituisce. Quindi un hard-link verso quel file viene
> "trascinato" alla nuova versione: lo snapshot precedente si corromperebbe. Il meccanismo è
> stato corretto di conseguenza (sotto). Lo spike resta come test che documenta questo
> comportamento e che valida il trucco "cancella-poi-robocopy".

Per un job versionato, ogni esecuzione reale:

1. Individua lo snapshot **precedente** più recente (se esiste).
2. Crea la cartella `dest\<timestamp>.inprogress`.
3. Se esiste un precedente: lo **clona via hard-link** nella nuova cartella (sottocartelle
   reali, file come hard-link → zero spazio extra).
4. **Pre-passata "rompi-cambiati" (solo metadati):** confronta la sorgente con il clone; per
   ogni file con **dimensione o data di modifica diverse** (o assente in sorgente), **cancella**
   la voce dal nuovo snapshot. Così l'hard-link si rompe e il file **resta intatto nello
   snapshot precedente**; inoltre quel file ora **manca** nel nuovo snapshot.
5. Esegue `robocopy /MIR <source> dest\<timestamp>.inprogress` con le opzioni del job:
   i file cancellati al passo 4 **mancano** → robocopy li **crea nuovi** (nessuna modifica
   sul posto, nessuna corruzione del precedente); i file immutati ci sono già e identici →
   robocopy li **salta** (hard-link al precedente preservato); i rimossi-in-sorgente vengono
   eliminati da questo snapshot.
6. A esito riuscito: rinomina `<timestamp>.inprogress` → `<timestamp>` e applica la ritenzione.

**Perché niente duplicazione e perché è corretto:** i dati statici stanno su disco **una sola
volta** (gli snapshot condividono i file immutati via hard-link); ogni snapshot aggiunge solo i
file **cambiati**. Non esiste alcuna cartella `latest` separata. La pre-passata cancella un
**sovrainsieme** dei file che robocopy toccherebbe (rompe il link per "dimensione o data
diverse", che include il criterio di robocopy "sorgente più recente o dimensione diversa"),
quindi robocopy non modifica mai sul posto un file ancora linkato al precedente.

**Timestamp:** formato `yyyy-MM-dd_HHmmss` (ordina cronologicamente, parsabile).

## Layout su disco

La destinazione di un job versionato contiene gli snapshot datati:

```
E:\Backup\Documenti\
   2026-06-28_150000\        ← ultimo backup (= stato corrente)
   2026-06-27_150000\
   2026-06-26_150000\
   2026-06-28_153000.inprogress\   (eventuale run in corso o interrotto)
```

Ogni cartella `<timestamp>\` è un albero completo navigabile. Le `.inprogress` non rientrano
nell'elenco versioni né nella ritenzione: rappresentano run in corso o interrotti.

## Componenti

### Core — logica pura (TDD)
- **`SnapshotPlanner`**: dati i nomi degli snapshot esistenti + ritenzione (`keepCount`,
  `maxAgeDays`) + `now` → nome del nuovo snapshot e lista di quelli **da eliminare**.
  Funzione pura (il tempo è un parametro). Ignora le `.inprogress`.

### Core — IO (test d'integrazione su cartelle temporanee)
- **`HardLinkCloner`**: clona ricorsivamente una cartella creando hard-link dei file
  (P/Invoke `CreateHardLinkW`, kernel32) e ricreando le sottocartelle come reali.
- **`SnapshotChangedUnlinker`**: la pre-passata "rompi-cambiati". Confronta la sorgente con il
  clone e **cancella** dal clone i file con dimensione o data di modifica diverse (o assenti in
  sorgente), così robocopy li ricrea nuovi senza modificare sul posto i file ancora condivisi
  con lo snapshot precedente. La logica di decisione è isolabile e testabile.
- **`HardLinkSupport`**: rileva se il volume di un percorso supporta gli hard-link, con un
  **test funzionale**: crea un file temporaneo nella destinazione, prova a creare un
  hard-link, pulisce; ritorna true/false. (Più affidabile del solo controllo NTFS.)

### Core — orchestrazione
- **`SnapshotService`**: per un job versionato esegue prev→clone→**rompi-cambiati**→
  robocopy(su `curr`)→rinomina→ritenzione e restituisce il `JobResult`. Riusa
  `RobocopyRunner`, `HardLinkCloner` e `SnapshotChangedUnlinker`.
- **`RobocopyArgsBuilder`**: aggiunta minima per usare un percorso di destinazione
  **effettivo** (lo snapshot `curr`) diverso da `job.Destination`, mantenendo sorgente e
  opzioni del job. Es. overload `Build(job, effectiveDestination, dryRun, logFile)`.
- **`BackupRunner`**: instrada i job con `Versioned == true` (e destinazione idonea) a
  `SnapshotService`; gli altri restano sul percorso attuale.

### Modello
- **`BackupJob`** nuovi campi:
  - `Versioned` (bool, default false)
  - `SnapshotKeepCount` (int, default 0 = nessun limite di numero)
  - `SnapshotMaxAgeDays` (int, default 0 = nessun limite di età)

### WPF — UI
- **Editor job**: toggle **"Mantieni versioni datate"** + campi N e giorni. Quando il toggle
  viene attivato, controllo **immediato** della destinazione con `HardLinkSupport`: se non
  idonea, avviso chiaro e **non si può salvare il job come versionato** (l'utente sceglie una
  destinazione NTFS o lo lascia mirror normale — scelta consapevole, non sorpresa).
- **Sfoglia versioni**: per un job versionato, elenco degli snapshot per data con pulsante
  **"Apri in Esplora risorse"** (`Process.Start("explorer.exe", folder)`), da cui l'utente
  copia ciò che gli serve. Nessun ripristino guidato in-app (fuori scopo v1.2).

## Ritenzione

Dopo un run riuscito: tieni gli ultimi **`SnapshotKeepCount`** snapshot **e** elimina quelli
più vecchi di **`SnapshotMaxAgeDays`** giorni. `0` su un limite lo disattiva (entrambi 0 =
nessuna pulizia, si accumulano). Eliminare uno snapshot rimuove solo i suoi hard-link: i dati
restano finché un altro snapshot li referenzia.

## Destinazione non idonea (exFAT / rete)

Coerente con la scelta "solo NTFS locale".

- **Difesa principale — alla configurazione:** il toggle versioning controlla la destinazione
  e blocca il salvataggio versionato su destinazione senza hard-link. Così il problema non
  arriva al run nel caso normale.
- **Caso raro — a run-time** (la destinazione è cambiata dopo: disco rimovibile riformattato,
  unità diversa): il job versionato trova la destinazione non idonea → **esegue comunque il
  backup come mirror normale** (priorità: non perdere dati) **ma segnala vistosamente** il
  fatto — il run è marcato e il log/banner dice "versioning non disponibile su questa
  destinazione: eseguito mirror semplice". Mai silenzioso.

Versioning su rete/exFAT: tappa successiva, fuori scopo v1.2.

## Flusso e gestione errori

- **Anteprima (dry-run):** nessuno snapshot creato; solo l'elenco robocopy come oggi.
- **robocopy fallisce:** lo snapshot resta `.inprogress` (escluso da elenco e ritenzione);
  l'esito registra l'errore. Nessuna rinomina.
- **Clone interrotto:** idem, `.inprogress` scartabile; nessun dato perso negli snapshot
  precedenti (sono indipendenti).
- **Primo backup di un job** (nessun precedente): salta il clone, robocopy copia tutto in
  `<timestamp>.inprogress`, poi rinomina.

## Test

- **Spike (primo task):** test reale che documenta che robocopy **modifica sul posto** (un
  hard-link verso il file aggiornato viene trascinato alla nuova versione) **e** che il trucco
  "cancella il file in destinazione poi robocopy" lo **ricrea nuovo** preservando la vecchia
  versione nello snapshot hard-linkato. Valida il meccanismo "rompi-cambiati → robocopy".
- **`SnapshotPlanner` (TDD):** selezione da eliminare per `keepCount`, per `maxAgeDays`, per
  entrambi; naming del nuovo snapshot; esclusione delle `.inprogress`; casi limite (0 = nessun
  limite, nessuno snapshot esistente).
- **`HardLinkCloner` / `HardLinkSupport` (integrazione):** su cartelle temporanee NTFS —
  clone crea hard-link reali (stesso contenuto, link count > 1); support rileva
  correttamente NTFS-sì / percorso-non-idoneo.
- Round-trip dei nuovi campi `BackupJob` nel config (come per i campi v1.1).
